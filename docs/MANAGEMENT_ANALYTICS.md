# รายงานสรุปและตัวชี้วัดการลา

เพิ่มในหน้าหลัก Manager/HR ตาม `codex_leave_app_fixes (2).md` ใช้ `src/ManagementAnalytics.jsx`, ตัวคำนวณอ่านอย่างเดียว `src/domain/managementAnalytics.js` และ CSV ใน `src/domain/managementExport.js` ใช้สี/กราฟเดิม ไม่เพิ่ม library กราฟ API หรือตารางยอดรวม

## ผู้ใช้และการตัดสินใจ

| ผู้ใช้ | ขอบเขต | ใช้รายงานเพื่อ |
| --- | --- | --- |
| Manager | Employee ที่ active ในทีมตน ไม่รวมตนเอง ผู้จัดการอื่น HR และทีมอื่น | วางแผนกำลังคนและติดตามคำขอของทีม |
| HR | พนักงาน active ทุกฝ่าย รวม Manager และ HR | เปรียบเทียบภาระการลา ตรวจสิทธิ์และทบทวนขั้นตอนพิจารณา |
| Employee | ไม่แสดงส่วนวิเคราะห์นี้ | ใช้หน้าสรุปการลาส่วนตัวเดิม |

ตรวจ actor/active จากฐานซ้ำแม้ได้รับ db เต็มหรือ role ปลอม การดูโปรไฟล์ข้ามฝ่ายไม่ใช่สิทธิ์อ่านรายงาน รายการฝ่ายมีเฉพาะที่มีสิทธิ์ ผู้จัดการส่งค่า HR/ฝ่ายอื่นเองไม่ได้ และ CSV ตรวจ scope เช่นเดียวกัน

## สูตรและช่วงข้อมูล

เลือกปี พ.ศ./เดือน/ฝ่าย/ประเภทลาได้ ยอดวันลาอ่านจาก `Leave_Day.date/units` ที่บันทึกไว้ ไม่คำนวณวันคำขอเก่าใหม่หรือเขียนข้อมูลกลับ

| ตัวชี้วัด | สูตร | ขอบเขต |
| --- | --- | --- |
| อัตราการลาในเดือนที่เลือก | [วันลา Approved + Pending บนวันทำงาน ÷ (วันทำงานในเดือน × จำนวนคน)] × 100 | รวมการลาที่รอผลและอนาคต จึงไม่ใช่อัตราขาดงานจริง |
| เปรียบเทียบเดือนก่อน | การ์ดแสดงอัตราของเดือนก่อนโดยตรง เพื่อเทียบกับอัตราเดือนที่เลือก | มกราคมเทียบธันวาคมปีก่อน ใช้ขอบเขต/จำนวนคนเดียวกัน; ค่า difference ใน domain ยังเป็นจุดเปอร์เซ็นต์ตามเดิม |
| เวลาอนุมัติเฉลี่ย | เฉลี่ย Reviewed_at − Request_date ของคำขอ Approved ที่มีวันลาในเดือน | ใช้ Decision ที่อนุมัติและไม่ cancelled ไม่ใช้ Consultation; นับคำขอหนึ่งครั้ง |
| ฝ่ายยอดลาสูงสุด | วัน Approved + Pending รายฝ่ายในเดือน | แสดงทุกฝ่ายที่ยอดสูงสุดเท่ากัน |
| ประเภทยอดลาสูงสุด | วัน Approved + Pending รายประเภทในเดือน | แสดงสัดส่วนต่อวันลารวม แยกสองสถานะ |

ฐานอัตราใช้จำนวนพนักงาน active และปฏิทินวันหยุด **ปัจจุบัน** ระบบยังไม่มีประวัติการจ้าง/ปฏิทินย้อนหลัง จึงแสดงสมมติฐานใต้ “วิธีคำนวณตัวชี้วัด” หักเสาร์–อาทิตย์/วันหยุดและนับไม่เกิน 1 คน-วันต่อคนต่อวันเพื่อไม่ซ้ำจากข้อมูลเก่า วันลาคลอดบนวันหยุดยังอยู่ครบในกราฟ/ยอดปฏิทิน แต่ไม่เพิ่มตัวเศษที่หารด้วยวันทำงาน

ไม่มีพนักงาน/วันทำงานแสดง “ไม่มีฐานคำนวณ” ไม่แปลง NaN/Infinity เป็น 0 ถ้ามีฐานแต่ไม่มีวันลาจึงแสดง 0% หากเวลาไม่ครบ ย้อนลำดับหรือเป็นอนาคต ให้ไม่นำมาคิด พร้อมจำนวนที่ข้าม; ถ้าไม่เหลือข้อมูลแสดง “ยังไม่มีข้อมูล” ไม่สร้างตัวเลขตามตัวอย่าง 3 นาทีหรือ 1.8% และไม่อ้างว่าเร็วขึ้นเท่าใดเมื่อไม่มีผลวัดกระบวนการกระดาษเดิม

## กราฟและตารางสิทธิ์

- กราฟฝ่าย/ประเภทใช้เดือนที่เลือก แยก Approved/Pending ด้วยสีและข้อความ ฝ่ายแสดงจำนวนคำขอ บัญชี active และคนที่มีลาอนุมัติวันนี้ ไม่เดาว่าคนที่ยังไม่บันทึกสถานะเข้าทำงานแล้ว
- แนวโน้มแสดงครบ 12 เดือนของปี ไม่หายตามตัวกรองเดือน เลื่อนบนจอแคบได้ และบอกว่า .5 คือครึ่งวัน
- ตารางสิทธิ์ใช้ **ทั้งปีที่เลือก** ใช้แล้ว/คงเหลือตามประเภท และ Pending แยกต่างหาก คงเหลือ = สิทธิ์จัดสรร − Approved ไม่หัก Pending ซ้ำ ยอด Approved รวมวันอนาคต
- ใช้ EMP code แยกคนชื่อซ้ำ ไม่ได้จัดสรรสิทธิ์ให้บอกข้อความ หากกรองลาคลอดแสดงสิทธิ์ตลอดแต่ละกรณี ไม่รวมเป็นสิทธิ์รายปี ส่วน Pending ของตารางยังนับเฉพาะปี
- สถานะวันนี้ยึดวันที่ไทยปัจจุบันและทุกประเภทลา ไม่เปลี่ยนตามตัวกรองเดือน/ประเภท ไม่มีข้อมูลแสดง “ยังไม่ได้ระบุสถานะ”

## กดดูที่มาของ KPI

การ์ดทั้ง 4 เป็นปุ่ม เปิดป๊อปอัปบนหน้าเดิมผ่าน `src/ManagementKpiDialog.jsx` พร้อมบริบทปี/เดือน/ฝ่าย/ประเภทที่กำลังเลือก:

- **อัตราการลา:** เห็นอัตรา วันลารวม จำนวนคนและวันทำงานก่อน รายชื่อรวมยอดต่อคนด้วย employee ID เรียงยอดมากไปน้อย พร้อม EMP code แยกชื่อซ้ำ กด “ดูวันที่ลาและคำขอ” เพื่อเปิดวัน/หน่วย/สถานะและคำขอต้นทาง สลับเดือนที่เลือกกับเดือนก่อน หากข้อมูลเก่าทับกันยังเห็นยอดคำขอจริงและยอดที่นับสูงสุด 1 วันต่อคนต่อวัน
- **เวลาอนุมัติ:** เห็นเวลาเฉลี่ยและจำนวนคำขอที่นำมาคิดก่อน แต่ละรายการแสดงชื่อพนักงาน ระยะเวลา เวลายื่นและเวลาอนุมัติ แสดงเหตุผลของเวลาที่ไม่ครบ/ผิดลำดับ/อนาคต ยอดเฉลี่ยใช้รายการเดียวกับการ์ด
- **แผนกและประเภท:** เลือกรายการแล้วเห็นยอดรวม แยกอนุมัติ/รอพิจารณา และคำขอทันที ส่วนอันดับทุกกลุ่มอยู่ใน “เปรียบเทียบทุกแผนก/ทุกประเภทการลา” ที่กดขยายได้ กรณีสูงสุดเท่ากันแสดงชื่อครบก่อนขยาย เริ่มจากรายการสูงสุดเมื่อมีเพียงรายการเดียว ไม่แสดง Rejected/Withdrawn ในคำขอที่ประกอบยอดนี้

ตามคำขอให้อ่านง่าย 15/10/2569 ป๊อปอัปใช้สรุปตัวใหญ่และรายการสั้นแทนตารางหลายคอลัมน์ สูตรอยู่ใน “วิธีคิดตัวเลขนี้” ที่ปิดไว้ก่อน บนมือถือไม่แสดงป้ายชื่อคอลัมน์ซ้ำทุกแถว ตัวกรองและข้อมูลต้นทางเดิมคงอยู่ ไม่มีการเปลี่ยนสูตร ยอดวันลา หรือข้อมูลที่บันทึก

ผลตรวจรอบปรับให้อ่านง่าย: UI ที่เกี่ยวข้องผ่าน 62 รายการ (Analytics 13 และ Workspace 49) รวมการรวมยอดต่อคน เปิดวันที่/ครึ่งวัน/คำขอต้นทาง พับสูตร และเลือกกลุ่มจากรายการเปรียบเทียบ ตรวจเบราว์เซอร์ Manager/HR ครบ 12 กรณีสองธีมที่ 1440/390/320px ทั้งเปิด–ปิดหัวข้อย่อย คืนโฟกัส คงตัวกรอง/scroll เปิดคำขอต่อ และ snapshot ไม่เปลี่ยน ไม่มีหน้าล้นหรือ page error; lint/JSDoc/build/format ผ่าน

กดเลขคำขอเปิดหน้ารายละเอียดเดิมตามสิทธิ์ อ่านอย่างเดียว ไม่ทำเครื่องหมายแจ้งเตือนหรือเปลี่ยนคำขอ ปิดด้วย ×, Esc หรือด้านนอก คืนโฟกัสไปการ์ดและคง URL/ตำแหน่งเลื่อน/ตัวกรองของ Dashboard ตัวกรองภายในป๊อปอัปไม่เขียนทับตัวกรองหน้าใหญ่ รายการจำนวนมากมี “แสดงเพิ่มเติม”

ป๊อปอัปใช้ Dialog เดิมผ่าน portal ไป body เพื่อไม่ติด transform ของ Dashboard หน้า App รับ `onAnalyticsDialogChange` ทำพื้นหลัง inert พัก NotificationToasts และปิดกั้นค้นหาด่วนระหว่างเปิด ปิดแล้วคืนพื้นหลังพร้อมกันก่อนคืนโฟกัส ทั้งตัวคำนวณและป๊อปอัปตรวจ actor/active/scope ล่าสุดอีกครั้ง หากสิทธิ์เปลี่ยนไม่แสดงข้อมูลเก่าค้าง

`rate.details`, `previousPeriod` และ `approvalDetails` เป็นผลคำนวณชั่วคราวเท่านั้น ไม่ใช่คอลัมน์ใหม่หรือ field ที่เขียนลง Database และไม่เปลี่ยนสูตร KPI/CSV เดิม

ผลตรวจรอบเปิดรายละเอียด 15/10/2569: Node ชุด Analytics 7 รายการ, Jest UI ทั้งชุด 111 รายการ, lint/JSDoc/build/format ผ่าน ตรวจเบราว์เซอร์ 12 กรณี (Manager/HR × 2 ธีม × 1440/390/320px) ครบทั้ง 4 ป๊อปอัป การสลับรายละเอียด กดเลขคำขอต่อ ปิด/Tab/Esc/คืนโฟกัส/คง scroll/ป้องกันค้นหาทับ และเทียบ snapshot ก่อน–หลังว่าไม่เปลี่ยนคำขอหรือสถานะอ่าน หลังแก้จังหวะปลด inert ตรวจกรณีคืนโฟกัสที่เกี่ยวข้องซ้ำผ่าน 5 รายการและเบราว์เซอร์ครบ ไม่มี page error หรือหน้าล้นแนวนอน

## CSV

ปุ่ม “ออกรายงาน CSV” ส่งออกบริบทตัวกรอง KPI และตารางรายคนที่มีสิทธิ์ ณ เวลากด ใช้ UTF-8 BOM สำหรับภาษาไทยใน Excel ตัวเลขเป็นค่าจริง เช่น 0.5 ช่อง comma/quote/newline ถูก escape และข้อความที่ขึ้นต้นคล้ายสูตรเติม apostrophe เพื่อไม่รันสูตรจากข้อมูลผู้ใช้

ไม่ส่งอีเมล เบอร์โทร เหตุผล ความเห็น เอกสารหรือรายละเอียดทางการแพทย์ ไม่สร้างแจ้งเตือนหรือแก้สถานะอ่าน และไม่แทนรายงาน snapshot ที่ส่ง HR เดิม หน้า `#/leave-summary` กับ `#/leave-report/:id` คงเดิม

## เกณฑ์อ้างอิงและขอบเขต

ตรวจ PDF `ชี้แจงงาน Assignment BIS-69.pdf` ที่ Downloads แล้ว: หน้า 12 Transaction → Report → Decision; หน้า 14 รายงานที่ช่วยตัดสินใจ; หน้า 26 Leave Summary/Balance/Absence Rate/Trend/Top Types; หน้า 57 ผู้ใช้/ข้อมูล/คำถามธุรกิจ/การตัดสินใจ; หน้า 60 Reports, Dashboard & Business Value จึงมีคำอธิบาย “ใช้รายงานนี้อย่างไร” ในแอป คะแนนยังขึ้นกับรายงาน การนำเสนอและการประเมินของอาจารย์

ไม่สร้างบทบาท Executive สมมติ ไม่เปิด HR ยื่นลาลงผู้จัดการ ไม่ขยายสิทธิ์ ไม่เปลี่ยน schema และไม่ seed/reset/ซ่อมฐานซ้ำเพื่อเพิ่ม Dashboard ใช้ IndexedDB v2 ที่แก้แล้ว ไม่เปลี่ยนฐานอีกเพียงเพราะเลขตัวอย่าง v6 ในไฟล์ ยังไม่ deploy หรือทำรายการกับ Supabase จริง การซ่อมข้อมูลรอบก่อนดู [FIXES_AUDIT.md](FIXES_AUDIT.md)
